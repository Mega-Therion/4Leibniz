# Formal Claims Contract (v1)

This directory defines the proof-grounded claim export published for
`4leibniz-web` and `leibniz-oracle` (issue #11). The contract has three parts:

1. **Schema** — `schema/v1/formal-claims.schema.json` (JSON Schema 2020-12).
2. **Artifact** — `artifacts/v1/formal-claims.json`, the committed catalog,
   regenerated by `scripts/generate_formal_claims.py`.
3. **Consumers** — `4leibniz-web` (packaged snapshot at
   `content/formal-claims-v1.json`) and `leibniz-oracle` (packaged snapshot at
   `assets/formal-claims-v1.json`). Both consume read-only; neither may
   produce or mutate claim statuses.

## Statuses

| status | meaning |
|---|---|
| `proved` | The pinned Lean toolchain checked the declaration: `lake build` succeeded, the module elaborates with zero `sorry`, and `#print axioms` reports nothing outside `{propext, Classical.choice, Quot.sound}`. |
| `conditional` | The claim holds only under recorded assumptions: a bare Lean `axiom` (assumed, never proved), or a checked theorem that depends on non-standard axioms — including `sorryAx`. The `conditional_on` array names each one. |
| `informal` | Not formalized in Lean; no formal verification is claimed. |
| `open_problem` | Recorded in `Leibniz.OpenProblems` as open or conjectured; explicitly not proved. |

## Honesty rules

- A failed Lean check **cannot** produce `proved`. Declarations that cannot be
  checked are **excluded** from the catalog — never silently relabeled — and
  the generator exits non-zero (CI treats that as a failure).
- If the toolchain is unavailable (`--no-lean`), the catalog contains only
  statically extracted entries (axioms, open problems) and no `proved` claim.
- Bare `axiom` declarations are catalogued as `conditional`, and every
  theorem that depends on them is `conditional` naming the axiom.
- Every theorem listed in `integration/4leibniz_bridge.json` (the RYTT
  bridge) must be catalogued; a missing one is a contract violation, not a
  degraded status.
- Consumers may explain any claim, but may label something *formally
  verified* only through the catalog's `proved` status. Their contract tests
  enforce this structurally (`verified_provenance` is null for everything
  else).

## Determinism and provenance

- The **claim list is a pure function of the checkout**: declarations are
  parsed from `Leibniz/**/*.lean`, sorted by `claim_id`, and serialized with a
  fixed shape (stable ids — fully-qualified declaration names, or
  `Leibniz.OpenProblems.<registry id>`).
- The artifact pins its `source.commit` (40-hex) and `lean_toolchain`;
  `generated_at` records when the verification run happened. CI can pin it
  deliberately with `--generated-at` or `SOURCE_DATE_EPOCH`.
- CI regenerates the catalog and compares the `claims` array against the
  committed artifact; a stale artifact fails the build.

## Reproducing locally

```sh
lake build                                   # pinned toolchain (lean-toolchain)
python3 scripts/generate_formal_claims.py    # → artifacts/v1/formal-claims.json
python3 -m pytest tests/test_formal_claims.py -q
```

## Refreshing consumer snapshots

Copy the artifact at a pinned commit:

```sh
cp artifacts/v1/formal-claims.json ../4leibniz-web/content/formal-claims-v1.json
cp artifacts/v1/formal-claims.json ../leibniz-oracle/assets/formal-claims-v1.json
```

Then run each consumer's contract tests
(`npm run test:contract` in 4leibniz-web, `npm test` in leibniz-oracle).
